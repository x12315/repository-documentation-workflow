# README 首屏重写设计

## 背景

当前 README 首段先定义项目类别，紧接着说明不适用场景。读者在看到项目能带来的结果和实现路径前，先遇到抽象定义与限制，无法迅速判断它为何值得使用。

本次只重写 README 的认知入口并调整现有章节顺序，不改变 Skill 运行时、能力边界、安装方式、版本或发布状态。

## 文档契约

- `primary reader`：正在使用 AI 编写或维护项目文档的开发者。
- `entry state`：已经有代码仓库和 AI 编程工具，但不满意 AI 生成文档的准确性、结构或可用性。
- `exit outcomes`：
  - 明白本项目通过流程约束提高 AI 文档质量，而不是提供一个只负责润色的 prompt；
  - 知道流程如何让文档更准确、更容易理解并能支持读者行动；
  - 能判断项目是否适合当前文档任务；
  - 能完成安装并开始使用；
  - 能区分已验证能力、尚未发布能力和验证边界。
- `document type`：explanation、how-to 与 reference 的组合；每节只承担一个主要目的。
- `reading mode`：hybrid；先建立项目模型，再进入安装和查阅细节。
- `scope`：README 负责项目定位、工作方式、安装入口、能力状态和验证边界；贡献、发布与安全细节转交专项文档。
- `mainline`：先展示 AI 文档写作可以获得的结果，再解释流程如何产生这些结果，随后给出安装和使用入口，最后说明证据与边界。

## 首屏文案

```markdown
# Repository Documentation Workflow

> 让 AI 写出的项目文档，不只是语句通顺，而是真的准确、好懂、能用。

Repository Documentation Workflow 为 AI 文档写作提供一套可执行的流程：先明确文档写给谁看，再核实项目事实、按读者的理解顺序组织内容，最后分别检查“读者能不能看懂”和“事实有没有写错或遗漏”。

它改进的是 AI 写文档的全过程，而不只是最后的措辞润色。
```

首屏不使用 `cold-reader`、`coverage reviewer` 或“双 reviewer”等实现术语。相关名称只在后文介绍完整工作流时定义；首屏直接说明两个检查分别回答的问题。

## 认知骨架

首屏文案后用四个步骤建立最小项目模型：

1. 明确文档写给谁看、读完要得到什么；
2. 从代码、配置和测试中核实可以写入的事实；
3. 按读者理解新概念的顺序组织内容；
4. 分别检查可读性与事实覆盖，未通过就继续修改。

README 后续章节按以下顺序组织：

1. 快速安装；
2. 适用与不适用场景；
3. 当前发布状态；
4. 完整工作流；
5. 验证证据与能力边界；
6. 贡献、发布与许可证。

现有开头的“不用于……”段落移动到适用范围；发布状态表移动到快速安装与适用范围之后。限制和状态不删除，只延后到读者已经理解项目价值和工作方式之后。

## 事实边界

- “准确、好懂、能用”是本流程的目标，不写成模型质量保证；后文继续说明确定性检查和真实 reviewer 证据的边界。
- Agent Skills CLI 的 GitHub 与本地 copy-install 状态保持现有、已验证的表述。
- OpenAI plugin 仍只声明 manifest 已准备，公开 marketplace 尚未发布。
- 当前版本、GitHub remote、tag 与 Release 状态保持已有事实。
- 暂缓的“文档体系完整性与单篇文档克制性”能力继续明确排除在 `0.1.0` 之外。

## 验收方式

- 只读标题、首屏和四步流程时，主要读者能复述项目结果、工作方式及其与普通润色 prompt 的区别。
- 首屏不要求读者预先理解内部角色名或 review 协议。
- 安装命令、路径、版本、发布状态和验证结论与仓库事实一致。
- README 本地链接和仓库完整验证通过。
- 实施后的 README 按 `repository-documentation-workflow` 运行 cold-reader 与 coverage reviewer；两者均通过后才交付。
