# 认知文档设计

本文用于设计文档身份、阅读方式和信息顺序。它不规定固定目录；同一内容只有在目标读者、阅读结果和 reading mode 相同的情况下才可复用结构。

## Document contract

写正文前先形成一份可审查的契约：

```text
primary reader: 主要读者是谁
entry state: 开始时知道什么、拥有什么、能执行什么
exit outcomes:
  - 读完后能准确回答的问题
  - 能做出的选择或完成的动作
document type: tutorial | how-to | reference | explanation
reading mode: linear | lookup | hybrid
scope: 本文负责什么，转交给哪些入口
mainline: 一句话说明理解如何展开
```

`primary reader` 只保留一个主要角色。其他读者可以受益，但不能让结构同时服从多个相互冲突的入口状态。`entry state` 写事实条件，不写“初级”“熟悉”等无法检验的标签。`exit outcomes` 应能转化为 reviewer 问题，例如“读者能指出 profile 与 adapter 的职责边界”，而不是“读者理解架构”。

## Reading mode

| 模式 | 读者行为 | 结构要求 | 常见文档 |
| --- | --- | --- | --- |
| `linear` | 从入口顺序读到结论 | 概念按依赖排序，阶段之间有桥梁 | tutorial、原理说明、首次架构导览 |
| `lookup` | 带着具体问题跳到条目 | 稳定分类、可预测标题、统一字段、交叉链接 | API/reference、配置字典、故障索引 |
| `hybrid` | 先建立全局模型，再按需查细节 | 短主线与查阅层分开，明确推荐路径 | README、架构入口、运维 playbook |

不要把按目录排列误认为 lookup，也不要把从头可读误认为 linear。模式描述的是读者如何取得信息；章节组织必须服务于该行为。

## 主线与骨架

主线是一条因果或任务脉络，不是主题列表。好的主线能回答：“读者为什么先知道这一点，下一部分又为什么出现？”

建立骨架时：

1. 列出 exit outcomes 所需的概念和事实。
2. 为每个概念标出前置概念，形成概念依赖。
3. 选择能覆盖最多依赖的一条端到端路径作为主线。
4. 把支线细节下沉到查阅层或短链，不中断主线。
5. 为跨组件、跨阶段或跨抽象层的跳转补认知桥梁。

认知桥梁通常只需回答三件事：刚得到什么结论、下一个问题为何自然出现、接下来保持哪个不变量。它不是总结套话；删除后若读者需要回读才能判断两节关系，该桥梁仍有作用。

## 渐进披露

第一层给方向：项目或模块是什么、为谁存在、边界在哪里、从哪里开始。第二层给模型：核心角色、依赖方向、主要数据或控制路径。第三层给细节：完整字段、参数、异常、变体和证据。

披露层级由读者任务决定，不由作者掌握信息的顺序决定。对新人隐藏必要前提会制造回读；在主线上展开所有边界情况也会淹没模型。判断一段内容的位置时问：读者在当前节点必须用它继续推理，还是只会在特定查询中使用它？

## 结构讨论

当存在实质不同的组织方式时，讨论 2–3 个方案。每个方案只比较以下维度：

- 哪个 entry state 最容易进入；
- 哪条 mainline 最短；
- 哪些概念依赖会前置或后置；
- 哪些内容进入主线，哪些进入查阅层；
- 哪些 exit outcomes 变得更容易或更困难。

推荐必须落到这些差异，不用“更清晰”“更完整”作为无证据结论。用户已经明确结构时，把它转换成契约和骨架；只有发现它无法满足 exit outcomes 或与事实边界冲突时才重新讨论。

## 首次接触检查

在进入独立 review 前，作者只做结构预检：

- 首个可见段落是否说明文档身份和读者能获得什么？
- 新术语是否在密集使用前得到定义或可达入口？
- linear 主线能否只读标题与每节首段仍被复述？
- lookup 条目能否由读者的问题稳定定位？
- hybrid 文档是否把推荐路径与完整细节分开？
- 每个 exit outcome 是否对应至少一个明确章节？

这些检查只证明骨架可送审，不代替 fresh-context reader。
